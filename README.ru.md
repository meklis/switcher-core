# Switcher-Core

PHP-библиотека, предоставляющая единый, независимый от вендора интерфейс для работы с сетевым оборудованием: коммутаторами, OLT и роутерами.

[English version](README.md)

## Обзор

Switcher-Core скрывает вендор-специфичные протоколы и наборы команд за одним API. Вместо того чтобы писать обёртку под каждого вендора, вы вызываете именованный **модуль** (например, `system`, `fdb`, `vlans`) у объекта `Device`, а библиотека:

1. Определяет модель устройства по SNMP `sysDescr` / `sysObjectID` (либо по явно указанному ключу модели).
2. Загружает соответствующую YAML-конфигурацию для этой модели (OID'ы, привязку модулей).
3. Передаёт вызов вендор-специфичной реализации модуля либо общей (shared/general), если отдельной реализации под вендора нет.

Набор модулей, поддерживаемых конкретным устройством, и точная форма ответа зависят от возможностей устройства и вендора. Это осознанный компромисс: единая строгая схема для всех вендоров недостижима при таком разнообразии сетевого оборудования. Как библиотека поддерживает максимально возможную консистентность ответов, описано в разделе [«Соглашение об именовании полей»](#соглашение-об-именовании-полей-в-ответах).

Если вашего оборудования нет в списке поддерживаемых — реализуйте классы модулей и конфигурацию, как описано в [Разработке модулей](docs/MODULE_DEVELOPMENT.md), и предложите изменения через PR, либо сопровождайте их в своём форке.

## Быстрый старт

```php
<?php
require __DIR__ . "/vendor/autoload.php";

use SwitcherCore\Modules\Helper;
use SwitcherCore\Switcher\CoreConnector;
use SwitcherCore\Switcher\Device;
use SwitcherCore\Switcher\PhpCache;

$deviceIp = '127.0.0.1';
$deviceCommunity = 'public';
$deviceLogin = 'login';
$devicePassword = 'password';

$coreConnector = new CoreConnector(
    // Путь к встроенному каталогу конфигурации библиотеки.
    // При необходимости скопируйте configs/ из vendor/meklis/switcher-core и меняйте её.
    Helper::getBuildInConfig()
);

$connector = ($coreConnector)
    // Необязательно, но рекомендуется. В продакшене используйте общий кеш (например, Memcached).
    ->setCache(new PhpCache());

$core = $connector->init(
    // init() определяет модель устройства и возвращает готовый к работе объект Device.
    Device::init($deviceIp, $deviceCommunity, $deviceLogin, $devicePassword)
        // Параметры подключения, здесь указаны значения по умолчанию.
        ->set('consoleConnectionType', Device::CONSOLE_TELNET)
        ->set('consoleTimeout', 10)
        ->set('consolePort', 23)
        ->set('snmpRepeats', 3)
        ->set('snmpTimeoutSec', 2)
        ->set('mikrotikApiPort', 8728)
);

echo json_encode($core->action('system'), JSON_PRETTY_PRINT);
```

## Соглашение об именовании полей в ответах

Некоторые модули (например, `fdb`, `pon_onts_status`) реализованы по-разному для разных вендоров и платформ, поэтому их вывод не может быть идеально единообразным. Библиотека последовательно придерживается одного правила:

* Поле **без подчёркивания в начале** — часть общего контракта модуля: одинаковое имя и смысл во всех реализациях этого модуля.
* Поле **с `_` в начале** — специфично для конкретной платформы/вендора и не входит в общий контракт.
* Если две платформы отдают семантически одно и то же значение под разными именами, для общего контракта заводится нейтральное имя, а исходное вендорское имя сохраняется рядом с префиксом `_` (например, общее поле `ident`, а также `_serial` у одной платформы и `_mac` у другой).

Интерфейсные объекты (`interface` / `interfaces`) следуют своей отдельной, уже устоявшейся конвенции: `id`, `name`, `type`, `parent` — общие; `_port`, `_slot`, `_onu`, `_snmp_id`, `_technology`, `_type` и т. п. — платформенные.

Подробности и примеры — в [Разработке модулей](docs/MODULE_DEVELOPMENT.md#response-field-naming-convention).

## Структура репозитория

| Путь | Назначение |
|---|---|
| `src/Switcher/` | Ядро, коннекторы, `Device`, обёртки консоли, кеш. |
| `src/Config/` | Чтение YAML и сборщики моделей, OID, модулей, трапов. |
| `src/Modules/` | Реализации модулей, по одному namespace на вендора/платформу. |
| `configs/modules.yml` | Реестр всех модулей и их аргументов. |
| `configs/models/` | Описания моделей устройств: правила определения и привязка модулей. |
| `configs/oids/` | Базы SNMP OID, сгруппированные по вендору/платформе. |
| `configs/traps/` | Конфигурация SNMP-трапов. |
| `docs/` | Сгенерированная документация по устройствам/модулям и примеры. |
| `src/Dev/`, `bin/console` | Локальная dev-консоль для вызова модулей и проверки поддержки. |
| `tests/` | Автоматические тесты. Сейчас покрытие ограничено проверкой консистентности конфигов, а не поведения на реальном железе. |

## Разработка и доработка модулей

Добавление поддержки новой модели устройства или нового модуля — это задача на стыке конфигурации и кода: файлы OID, описание модели и (если ни один существующий модуль не подходит) PHP-класс. Полностью описано в [Разработке модулей](docs/MODULE_DEVELOPMENT.md).

## Тестирование

```bash
composer tests
```

Запускает набор PHPUnit (`tests/`), который сейчас проверяет консистентность конфигурации (OID, модели, модули). Он **не** проверяет поведение на реальном оборудовании — автотесты здесь не заменяют проверку на настоящем устройстве. Как это делать через `bin/console`, см. в [Разработке модулей](docs/MODULE_DEVELOPMENT.md#testing-against-real-devices).
